## 第一轮测试边界

本轮测试从公开行为进入，不反射私有字段、不通过测试副本重算生产算法。

1. **Runtime 角色世界入口**：注册居民日程，输入世界时间，查询角色状态、取出语义事件，提交或取消有期限的活动候选。
2. **Unity 居民生活入口**：绑定真实 `IWorldTimeFlow`，经控制器提交活动，观察 `NpcWorldResident2D` 的位置、目的地、在家状态及路线状态。
3. **既有时间与读档入口**：通过 `DaytimeClock`、`WorldTime`、`GameSave` 驱动推进与重建，验证旧请求失效及日程恢复。

候选行为逐条执行 RED → GREEN；先确认测试因缺少目标行为失败，再补充最小实现。测试替身只用于时间或未来模型等外部边界。

## 第一轮场景

| 场景 | 预期可观察结果 |
| --- | --- |
| 初始注册、连续小步走时、跨日程边界 | 每名居民有独立状态；不为每帧生成事件；边界变化进入对应居民队列 |
| A 接受临时活动 | A 的目标不被日程更新覆盖；B 保持自己的日程 |
| 活动到期或主动取消 | 恢复当前时刻的默认日程；不能恢复已经过时的旧目标 |
| 时间一次跨过活动期限 | 到期前后各段都从实际位置推进，避免整段错误执行旧活动或瞬移 |
| 未知目标、非法期限、忙碌、旧版本或重复请求 | 返回明确拒绝，既有活动和位置不发生额外变化 |
| 读档、重绑其他世界、同一世界重复绑定 | 新时间线拒绝旧候选；同一绑定保持当前活动与位置 |
| 多次事件或长时间无人取出事件 | 队列有界，过时同类通知合并，保留最新相关信息 |

第一轮的临时活动表示“接受了目的地与停留期限”，实际到达由移动层报告；不把接受动作当作生产、交付或完整社交已完成。

## 回归范围

- 修改前运行既有日程测试，建立本次基线。
- 每个 Runtime 行为切片运行目标测试，最后运行完整 EditMode。
- Unity 接线运行活动仲裁测试及既有 `TownLifePlayModeTests`、四居民日程、动画和时间相关测试，再运行完整 PlayMode。
- PlayMode 使用图形模式；测试命令不带 `-quit`。所有结果使用独立的 `Logs/agent-world-*` 文件名。
- 共享工作区的历史结果不作为本轮通过证据；新失败先定位来源，再判断是否属于本次改动。
- 实际模型评测与模拟测试分开，计费服务接入时核对现有场景验收和新行动契约。

## 后续测试重点

第四轮补充评测：[验证双人资源协作的多初始场景](https://github.com/qinjunw/CozyTown/issues/60) 按用户要求，在进入四人跨日验证前增加 4 种初始配置 × 3 次真实运行。每轮重建双方状态及实际场景，先验证初始化，再允许模型调用；正常库存、卖方缺鱼、买方缺钱、买方已有鱼分别统计。模型行为选择与宿主资产约束分开评价，失败计入原轮次。整个实验一个代理、96 次提供方调用上限，每轮最多 12 次；沿用公开经济快照、决策客户端与 Unity 居民控制器边界。[运行方式和分类](../../../Tools/agent_proxy/README.md#多初始场景评测) 定义输入与证据文件。此实验覆盖独立双人运行，四人跨日和读档仍需后续验证。

第四轮公开边界按用户“开始下一阶段”的授权确定：经济状态入口一次提交两个角色候选；资源会面入口绑定宿主给定的鲤鱼数量与价款，验证双方同意、实际到达、交付凭据和重复请求；决策入口仅披露固定条款及本人相关资产；真实场景观察 Sora 缺料触发、Ren 答复、交付与日程恢复。默认演示条款为 1 条鲤鱼换 25 金币，沿用现有鲤鱼出售单价。新游戏给 Ren 2 条鲤鱼、Sora 50 金币和 1 份盐作为明确的初始资产；不把初始资产描述成已完成的捕鱼或生产。原有配方通过 Sora 自己的背包验证。

第四轮依次验证 RED → GREEN：双方提交及守恒；缺料、资金不足、满包、溢出时无部分更新；同意和到场门禁、取消、旧时间线、重复交付；缺料自动触发和资源上下文隔离；角色资产存取与仅含玩家的旧存档升级；Unity 真实路线及模型代理。新证据使用 `Logs/agent-resources-*`。真实模型仍用 `deepseek-v4-flash`，本轮代理最多 10 次调用，不自动重试；跨日经历与进行中承诺持久化仍由第五轮验证。

第三轮公开测试边界按用户继续下一阶段、使用 v4-flash 并授权真实 Key 测试的指令确定：通过 Runtime 会面入口提交邀约与答复，观察双方活动、地点预约、轮次和本人经历；通过既有调度入口验证自动触发；通过 Unity 居民控制器观察实际赴约、交谈和日程恢复；通过代理 HTTP 入口验证模型协议和有界真实调用。外部模型、单调时间和位置报告是测试输入，不读取私有实现。每个新行为先验证 RED，再补实现。

第二轮公开边界按用户“推送后继续按照计划做下一阶段重构”的授权确定：通过 Runtime 决策调度入口输入权威世界状态与单调现实时间，在模型客户端这一外部边界使用固定替身，观察输出请求、活动结果和调度诊断；通过 Unity 居民控制器观察自动触发后的实际位置；代理协议通过公开编解码入口验证。测试不读取私有调度状态。

第二轮依次验证：休息机会自动触发且不逐帧调用；真实请求的并发与滚动预算；同一决策内按需披露；旧世界、旧修订和过时机会拒绝；超时／取消后保留实际在途请求槽；Unity 活动接线。每个新行为先出现测试失败，再增加实现。

- 决策：并发与预算、迟到结果、上下文隔离、工具续调上限、断线回退。
- 社交：同时邀请、重复接受、参与者忙碌、路径失败、超时释放、实际赴约和对话记忆。
- 资源：双方原子更新、数量和资金守恒、失败状态不变、重试去重。
- 持久化：旧时间线信息隔离、进行中承诺恢复或取消、连续多日记录。
- 模型：固定场景的多次运行、人设与行为差异、实际完成率、用量、延迟和失败分类。

局部观察阶段按用户 2026-09-13 的选择优先推进，见[专项规格](../../AGENT_LOCAL_OBSERVATION_SPEC.md)：从实际区域＋距离筛选少量已登记对象，分别表达当前事实、历史观察、参与者声明和未知；同一事实快照下比较自由台词与结构化表达后再选择正式方案。先完成观察、时效与权限的公共行为检查，再做两个表达组的固定请求和新建双方场景。规格列出最多 96 次提供方调用的实验草案；本次设计阶段没有执行这些测试或调用模型。
