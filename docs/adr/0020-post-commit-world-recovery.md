# ADR-0020：提交后同步失败时暂停世界协调与 NPC 行动

- 状态：Accepted。
- 日期：2026-09-17。
- 票据：[明确读档提交后重建失败的处理边界](https://github.com/qinjunw/CozyTown/issues/91)。
- 运行证据：[读档重建失败验证](../verification/npc-load-recovery-2026-09-17.md)。

## 事实与选择

schema v3 的五个存档模块恢复成功后，存档数据已经提交。NPC 身体、执行代际和会面随后通过时间通知重建；Unity 组件或订阅者仍可能抛异常。原同步委托会中断余下订阅，因此不能把这种异常解释为“读档未发生”。

提交前准备全部身体可以提前发现部分错误，但仍无法保证 Unity 提交和外部通知不失败，而且需要改变存档层与场景层的协调协议。本轮保留现有提交点，增加提交后的恢复状态。未来完整快照仍按 ADR-0019 在提交前校验和准备；提交后的运行对象异常继续适用本决策。

## 同步契约

`IWorldTimeFlow.State` 有三个值：`Ready` 允许协调操作，`Publishing` 表示操作或通知尚未完成，`RecoveryRequired` 表示必须修复故障并重新读档。`Current` 在通知前更新；恢复失败时，不能把它或 NPC 身体视为全部模块的一致视图。

`Changed` 是关键同步订阅。宿主逐一调用全部订阅者，收集异常；一个失败不阻止后续 NPC 尝试重建。只有全部关键订阅成功才发送 `PresentationChanged`。灯光及农场／鸡舍显示使用后者，显示失败继续通知其他显示对象。通知期间拒绝嵌套读档、保存、时钟推进、睡眠、NPC 行动、换绑及决策重配。

| 结果 | 返回与状态 | 恢复方式 |
| --- | --- | --- |
| 解析、校验或模块返回失败，补偿成功 | 保留原业务错误；原状态、余量及候选资格保持 | 修正输入后重试 |
| 存档已提交，关键同步失败 | `save.loaded_rebuild_required`；`RecoveryRequired` | 修复订阅／组件，重新读取有效存档 |
| 存档已提交，只有显示失败 | `save.loaded_presentation_failed`；`Ready` | 修复显示；后续通知重新刷新 |
| 回滚本身返回失败 | 保留 `save.rollback_*`；`RecoveryRequired` | 修复恢复组件后重新读取有效存档 |
| 恢复实现抛异常，无法确认提交程度 | `save.restore_exception`；`RecoveryRequired` | 核对诊断并修复恢复组件，再读取有效存档 |

普通时间推进与睡眠使用同一通知策略，提交后分别返回 `world_time.synchronization_failed` 或 `world_time.presentation_failed`。因此调用者不能根据 `IsSuccess == false` 推断时刻未变，也不能盲目重试同一推进量。读取 `Current`、`State` 和 `NotificationFailures` 确认实际状态。诊断只记录阶段、订阅方法和异常类型，不保存异常消息中的任意内容。

## 恢复期间的约束

暂停范围是存档门面、时间协调器和 NPC 行为入口。禁止继续推进时间、覆盖存档、提交／取消 NPC 活动，以及替换调度器。查询和修复场景组件仍可进行。底层模块的 `Restore`／`Commit` 是状态接口，不由此机制统一加锁；调用者应经协调器执行游戏用例。

调度器失效化旧逻辑请求，发出取消信号，但保留未完成 Task、并发占用、角色冷却及真实时间调用窗口。暂停时可回收已经完成的 Task，但不应用回复、不观察会面或消费世界触发事件。关键同步完整成功后恢复调度；重新读档建立新执行代际，旧回复仍不可写入。

恢复期间读到坏档或缺档不会解除原来的暂停。schema v3 的有效重读档仍清空会面、按日程归位并清零小数分钟；本决策不新增完整快照字段。普通走时故障且尚无有效存档时，需要修复故障后重新建立会话；本轮不提供保留当前部分重建状态的就地续跑。

任意恢复实现抛异常后的补偿细化仍需单独验证；本轮采用保守暂停，不能声称这些模块已完整回滚。完整逻辑快照不得以“捕获异常并继续运行”替代本契约。
