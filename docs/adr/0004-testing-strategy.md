# ADR-0004：以 EditMode 组件测试作为业务规则主验证层

- 状态：已接受
- 日期：2026-08-28

## 背景

当前阶段首先搭建模块接口和确定性实现，尚未完成小镇场景、UI、输入绑定、文件存档适配器或线上 AI 适配器。业务规则需要在这些集成完成前获得快速、可重复的验证。

Unity 项目使用 Unity Test Framework `1.4.5`。运行时与测试源码已经通过独立 Roslyn 编译，15 个 NUnit 用例的方法级离线执行结果为 15 passed、0 failed。批处理启动日志确认当前环境没有有效 Unity Editor 许可证，Editor 以代码 `198` 终止，因此 Unity Test Runner 尚未执行。

## 评估选项

### 选项 A：只进行人工 PlayMode 演示

可以观察最终体验，但余额不足、部分扣除、重复跨日和损坏存档等边界难以稳定复现，也不能在场景完成前验证模块。

### 选项 B：以 EditMode 组件测试为主，按集成阶段增加 PlayMode 和人工检查

普通 C# 模块在 EditMode 中直接构造，随机结果使用显式输入，文件系统和 AI 使用固定替身。场景接入后再为绑定与交互增加少量 PlayMode 测试。

### 选项 C：从当前阶段建立完整端到端自动化

需要先固定场景、UI、输入和构建目标，会让测试依赖尚未确认的表现层设计。

## 决策

采用选项 B。

### 测试分层

1. **EditMode 组件测试**：覆盖每个模块的不变量、边界条件和结果对象，是当前阶段的主验证层。
2. **EditMode 协作测试**：覆盖购买、出售、烹饪、跨日结算和保存快照等跨模块流程。
3. **PlayMode 测试**：场景接入后覆盖控制器绑定、交互触发、UI 刷新和场景生命周期。
4. **AI 离线评测**：使用固定输入集测量结构有效率、人设一致性、世界状态矛盾和越权诱导结果。
5. **人工演示检查**：发布作品版本前按固定脚本完成经济闭环、服务故障回退和存档恢复。

### 隔离规则

- 默认自动化测试不访问网络、不调用计费模型、不读取真实玩家存档。
- 钓鱼组件测试向 `Catch(int roll)` 传入固定值；随机数生成留在后续用例或表现适配层。
- 日期推进使用显式 `Day` 值，不读取操作系统时钟作为游戏天数。
- AI 测试使用固定生成器、故障替身和保存的响应夹具。
- 文件存档测试使用测试专用临时路径，不使用开发者真实槽位。
- 每个测试创建自己的对象图，不依赖测试执行顺序或静态可变状态。

## 组件覆盖清单

| 模块 | 必需成功路径 | 必需拒绝或故障路径 |
| --- | --- | --- |
| Time | 推进一天 | 非法初值或重复结算保护 |
| Inventory | 增加并移除物品 | 非法数量、库存不足 |
| Economy | 完成购买和出售 | 余额不足、库存不足、任一失败不部分提交 |
| Farming | 播种到成熟并收获 | 错误种子、未成熟、重复结算 |
| Livestock | 喂食后产出鸡蛋 | 未喂食、重复领取 |
| Fishing | 固定成功结果进入背包 | 失败结果、背包拒绝 |
| Cooking | 消耗全部食材并生成料理 | 食材不足、成品拒绝且无部分扣除 |
| Npc | 返回固定对话 | 超时、异常或无效响应回退 |
| Save | 写入并读取同一快照 | 空槽、损坏数据、未来版本 |
| Core | 默认服务完整且依赖一致 | 缺失注册在测试中失败 |

当前骨架可以先覆盖接口已表达的路径。依赖场景、文件格式或线上服务的测试在相应适配器落地时增加，不能用空断言占位。

## 退出条件

### 架构骨架阶段

- Unity Test Runner 能发现 `CozyTown.Tests.EditMode`。
- 每个已实现模块至少有一个可观察行为测试。
- 余额不足、库存不足或食材不足时，无跨模块部分提交。
- 默认组合根可以在测试中创建全部类型化服务。
- 测试代码不包含联网模型调用和机器专用路径。

### 可玩 MVP 阶段

- 所有 EditMode 组件与协作测试通过。
- 关键小镇交互具有 PlayMode 冒烟测试，或记录无法自动化的原因和人工脚本。
- 当前存档版本的往返测试及所有支持版本迁移测试通过。
- AI 故障注入回退测试全部通过；离线评测报告包含样本数、模型版本、提示词版本和指标结果。
- 人工演示从新游戏完成一次生产经济闭环，并在重新加载后核对持续状态。

## 执行方式

Editor 内使用 **Window > General > Test Runner** 运行 EditMode 测试。

批处理命令模板：

```powershell
Unity.exe `
  -batchmode `
  -nographics `
  -projectPath <project-root> `
  -runTests `
  -testPlatform EditMode `
  -testResults <project-root>/Logs/EditModeTests.xml `
  -logFile <project-root>/Logs/EditModeTests.log `
  -quit
```

批处理结果必须同时检查 `EditModeTests.xml` 和日志中的编译、测试或许可证错误。Windows 上的 Unity 启动器可能先返回 `0`，而 Editor 进程随后在日志中以代码 `198` 终止，因此不能只使用 PowerShell 的 `$LASTEXITCODE` 判断。当前报告状态应写“未执行：Unity Editor 许可证未激活”。在 Unity Hub 激活许可证后重新运行该命令并检查本次生成的 XML 与日志。

## 后果

正面结果：

- 业务规则可以在场景和美术完成前持续回归。
- 故障替身能稳定覆盖 AI 和存档异常路径。
- PlayMode 测试数量由 Unity 集成风险驱动，不重复验证纯 C# 规则。

成本和风险：

- EditMode 测试不能发现碰撞体、序列化引用、Canvas 或输入绑定错误。
- 固定替身不能代表真实模型的延迟和内容分布，需要单独离线评测。
- 批处理许可证和 Unity 导入状态会影响自动化可用性，验证报告必须区分测试失败与基础设施失败。

## 复审条件

确定持续集成平台、目标构建平台或联网服务环境后，复审批处理命令、PlayMode 范围、测试报告归档和密钥注入方式。业务组件继续以 EditMode 测试为主，除非测量表明其行为依赖 Unity 运行时。
