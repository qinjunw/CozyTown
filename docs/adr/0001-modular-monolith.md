# ADR-0001：使用 Unity 项目内的模块化单体

- 状态：已接受
- 日期：2026-08-28

## 背景

MVP 在一个 Unity 客户端内运行，包含时间、背包、经济、种植、畜牧、钓鱼、烹饪、NPC 和存档模块。当前阶段需要先建立模块边界和测试入口，尚无独立部署、网络同步或多团队发布需求。

需要同时满足以下约束：

- 场景和 UI 可以逐步接入，不把业务状态绑定到 `MonoBehaviour` 生命周期；
- 单个系统可以在 EditMode 中独立测试；
- 跨系统交易必须能明确检查依赖和原子性；
- 项目规模不支持维护多个独立服务和协议版本。

## 评估选项

### 选项 A：按场景脚本直接实现

每个交互对象持有其他对象引用并直接修改状态。初始文件较少，但业务规则会依赖场景加载和对象查找，跨模块测试需要构造场景，存档也需要读取 Unity 对象状态。

### 选项 B：每个模块独立 Unity Package 或运行时程序集

编译边界最强，但需要立即维护多个程序集依赖、测试程序集和资源访问规则。当前没有独立发布或平台差异要求支持该成本。

### 选项 C：单运行时程序集内的模块化单体

使用 `Assets/CozyTown/Runtime/<Module>` 目录、对应命名空间和窄接口表达边界。一个组合根创建实现，场景层只依赖公共入口。EditMode 测试位于独立测试程序集。

## 决策

采用选项 C。

- 运行时代码位于 `CozyTown.Runtime` 程序集。
- `Application`、`Content`、`Core`、`Time`、`Inventory`、`Economy`、`Farming`、`Livestock`、`Fishing`、`Cooking`、`Npc` 和 `Save` 使用目录与命名空间分区。
- 跨模块调用通过接口和 DTO；调用方不能修改其他模块的内部集合。
- `CozyTownCompositionRoot.CreateDefault()`、`Create(configuration)` 和 `CreateEmpty()` 显式创建对象图，并以 `CozyTownServices` 的类型化属性公开服务。
- Unity 生命周期适配位于单独的 `CozyTown.Unity` 程序集；它可以依赖 Runtime，Runtime 不依赖 UnityEngine。完整服务集合只在组合边界使用，不能作为场景服务定位器公开。
- 禁止全局静态服务定位器、运行时 `Get<T>()` 容器和通过场景查找取得领域服务。
- `CozyTown.Tests.EditMode` 引用运行时程序集；`CozyTown.Tests.UnityEditMode` 引用 Unity 适配程序集。

## 后果

正面结果：

- 业务组件可以在不加载场景的条件下构造和测试。
- 默认对象图集中可见，依赖替换不需要修改业务调用方。
- 后续 Unity 控制器可以逐模块接入，而不改变未接入模块。

成本和风险：

- 单运行时程序集不会在编译期阻止所有模块越界；代码评审和测试需要执行依赖规则。
- 跨模块用例需要显式协调器，不能把流程隐藏在 UI 脚本中。
- 模块接口过宽会形成事实上的共享状态，因此公共成员需要按已确认用例增加。

## 复审条件

出现以下任一可观察条件时评估拆分运行时程序集或 Package：

- 模块产生无法通过接口或协调器解除的循环依赖；
- 某模块需要独立平台实现或独立发布；
- 编译时间测量表明单程序集修改造成不可接受的迭代延迟；
- 多个团队需要独立所有权和版本边界。

拆分前保留现有命名空间和公共契约，避免仅为目录调整改变业务行为。
