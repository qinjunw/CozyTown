# 连续世界时间与定时结算：调研方案

- 日期：2026-09-05；本地代码审计基准：`5a0d68c`。
- 状态：Research / Proposed。用户要求先完成调研与方案，不改游戏代码。
- 需求方向：允许跨午夜走时；世界机制依游戏时间更新；NPC 可分别配置作息；睡眠推进世界时间。
- 未确认参数：每日结算时刻、可选睡眠时长、是否有凌晨强制结束规则。下文的 `05:00` 和 `1～12 小时` 仅为讨论示例。
- 依据：[同类游戏规则](game-time-precedents.md)、[公开实现模式](time-advancement-patterns.md)。公开玩法资料不证明闭源游戏采用某一种内部架构。

## 1. 结论

建议提供一个统一的**世界时间推进模块**，由正常走时和睡眠快进共用；农田、畜牧、商店和 NPC 保留各自规则，通过窄接口参与推进。它们不继承时钟类，也不各自维护独立日期。

时钟负责“现在是什么时候”；时间推进用例负责“从旧时刻到新时刻跨过了哪些边界、哪些更新必须共同成功”；领域模块负责“到这个边界，自己的状态怎样改变”。这是组合关系：商店**依赖时间**，但商店**不是一种时钟**。

当前只有少量领域模块和四名 NPC，使用显式调用与配置表即可。不需要为此引入数据库、消息中间件、可动态注册任意回调的调度平台，或全局 `TimeDependentBase` 继承树。

## 2. 区分四个概念

| 概念 | 拟议含义 | 示例 |
| --- | --- | --- |
| 世界时刻 | 唯一权威的游戏日期和时分；推进时单调递增，读档是明确的恢复操作 | Day 2 00:10 |
| 自然日期 | 午夜递增的日历日期，不自动代表生产已结算 | 23:59 后进入次日 |
| 定时结算 | 穿过某个机制的生效时点后，执行一次状态转换 | 05:00 结算生产并刷新商店 |
| 睡眠快进 | 请求推进一段游戏时间，经同一套规则处理途中边界 | 23:00 睡至次日 07:00 |

“每日结算”不等于每个系统都只能每天更新：作物可按每日周期成长，商店按每日补给点换库存，NPC 按个人时段改变目标。未来若有加工计时器，可按完成时刻结算，但本阶段不新增加工或出货系统。

时间点不同的机制不必强行共享一个“业务日期”整数。首版生产和商店若共用晨间边界，可以共用结算标记；NPC 的 07:00 出门不需要制造第二份日期状态。具体字段在存档决策时确定。

“连续走时”在本需求中首先指跨午夜不封顶，不要求每毫秒模拟世界。建议先按游戏分钟表达规则，把权威时间推进与 UI 十分钟一跳的显示分开；只在出现分钟无法表达的规则时再评估更细精度。移动和动画仍可逐帧更新。

## 3. 模块职责与接口方向

```text
Unity 有效游玩秒数 ─→ 倍率/余量换算 ─┐
                                    ├→ 世界时间推进用例
睡眠选择 ─────────→ 游戏分钟请求 ───┘      │
                                          ├─ 找出跨越的时点并按先后处理
                                          ├─ 生产结算：作物、畜牧规则
                                          ├─ 商店补给：确定库存、保留钱包
                                          ├─ NPC 日程：各自目标与行程状态
                                          └─ 提交一致快照 → UI / 场景表现
```

- **时刻模型**：复用日期/分钟概念，以整数分钟比较先后。不要以浮点帧计时作为库存或成长周期的身份。
- **时间推进用例**：对调用方只暴露推进请求与成功/失败结果，不要求调用方逐个通知商店、农田和 NPC。
- **生产和补给**：继续封装浇水、喂食、待领取产物、库存替换和守恒约束。时间模块不知道某种作物需要几天，也不持有报价表。
- **NPC 日程**：按稳定 NPC ID 配置活动时点和目的地。日程确定目标，路线/移动负责实际到达；到点不能把尚在路上的人描述为已到家。
- **呈现层**：在状态提交后更新显示。动画每帧播放不等于每帧重复结算生产。

首版可保留各领域已有接口，由应用层显式编排。只有多个实现确实共享同一个“结算参与者”契约时才提取小接口；不为了接口外观一致给无关模块添加空方法。状态提交前的关键业务失败不能交给无法回滚的广播事件处理。

现有农田和畜牧的 `AdvanceDay` 直接修改当前状态。若采用下述候选计算与统一提交，需要在模块内部提供候选状态计算或适配，不能只调整现有方法的调用顺序就声称具备整段原子性。

“深模块、浅接口”的衡量点是调用方不必知道结算顺序、重试、跨午夜和存档标记，而不是把所有领域逻辑搬进一个巨型管理器。

## 4. 关键推进规则

### 穿越边界，不轮询时钟是否恰好等于某一刻

一次请求检查 `(旧时刻, 新时刻]`。若 04:59 一次推进 10 分钟，05:00 仍须执行一次。重复评估同一时刻或恢复同一份存档，不应再次刷新库存、成长或领取产物。

结算标记必须随存档保存。加载负责恢复已提交状态，不把恢复动作误当作又经历了一遍时间。新游戏 Day 1 06:00 的初始库存已经建立，不能在首次 Update 再刷新一次。

### 快进与正常推进共用业务规则

在相同初始状态、没有中途玩家操作的条件下，分段推进和一次睡眠快进应得到相同的生产、库存和目标时刻结果。睡 2 小时而未跨生产边界，不凭空获得一整天的成长；跨过午夜也不立即触发晨间补给。

跨多个结算周期时按先后计算，不能直接把农田的最后结算日设为最终日。时间相同的多个更新采用明示顺序，例如先生产/补给，再更新居民目标，最后发布显示；具体顺序须由测试固定。

推荐一次已接受的快进请求整体成功或整体失败：先在候选状态计算，全部成功后发布，失败保留请求前的时钟、资产和结算标记。处理时长上限与溢出规则需在实施前确定，不能把“无日末封顶”解释成对任意大输入无限循环。

失败时也保留计时余量，不提前发布新的 NPC 目标、位置或行程状态。推荐自动推进跨边界后保留未消费余量，成功睡眠/加载清零，失败请求和保存保留余量；这沿用现有显式跳时的余量约定，不等于已保存亚分钟进度。

### NPC 不必逐动画帧补演整晚

正常游玩时沿合法路线连续移动。睡眠期间可按游戏时间段计算路线进度，无需渲染每一步；要定义跨日程切换、受阻、归家和剩余行程的结果。不能只把最终目标改成“厨房”，就宣称 NPC 在快进期间已经走到了厨房。

路线受阻是可报告的正常移动结果，不应自动当作整个时间请求失败；时钟继续推进，NPC 保留合法位置及受阻状态。真正的领域计算或状态提交失败才进入时间请求的失败处理。

当前 T1 允许加载后按时段合法归位。这与睡眠期间如何推进是两个独立约定；本轮不把加载重建自动改为精确位置存档。NPC 职业表现仍不自动生成物品、交易或调用模型。

自动走时继续尊重模态/失焦暂停。睡眠是用户明确请求的游戏时间推进，不受选择睡眠时弹出的模态暂停影响；失焦不补算现实离线时间。

## 5. 当前代码与重构影响

| 证据入口 | 当前行为 | 实施时需要改变的边界 |
| --- | --- | --- |
| [DaytimeClockCoordinator](../../../Assets/CozyTown/Runtime/Application/DaytimeClockCoordinator.cs) | 把推进分钟数钳制到 23:59 | 替换为跨边界推进；保留倍率、有效时间与余量控制 |
| [InMemoryTimeService](../../../Assets/CozyTown/Runtime/Time/InMemoryTimeService.cs) | 已能进行跨午夜的分钟运算 | 可复用算术，但不能绕过领域结算直接供 Unity 写入 |
| [DayTransitionCoordinator](../../../Assets/CozyTown/Runtime/Application/DayTransitionCoordinator.cs) | 睡觉同时递增日期、设为 06:00 并结算生产和商店 | 拆开“目标时刻”与“每日结算”；不能原样在 05:00 调用，否则又加一天 |
| [GameSaveCoordinator](../../../Assets/CozyTown/Runtime/Application/GameSaveCoordinator.cs)、[快照校验器](../../../Assets/CozyTown/Runtime/Save/GameSaveSnapshotValidator.cs) | 要求农田、畜牧、商店结算日全部等于时钟日期 | 允许午夜后、晨间边界前的合法未结算状态，同时防重复/未来标记 |
| [农田](../../../Assets/CozyTown/Runtime/Farming/InMemoryFarmService.cs)、[畜牧](../../../Assets/CozyTown/Runtime/Livestock/InMemoryLivestockService.cs) | 只接受连续的下一个结算日 | 保留逐周期成长/喂养语义，不用跳到最终日期代替计算 |
| [库存替换策略](../../../Assets/CozyTown/Runtime/Economy/DeterministicShopStockReplacementPolicy.cs) | 同一天重复请求不重抽，刷新保留商店钱包 | 保留算法确定性及交易守恒，明确种子中的日期对应哪个补给周期 |
| [JSON 存档](../../../Assets/CozyTown/Runtime/Save/JsonFileSaveStorage.cs) | v1 / v2 读取分支依赖当前版本常量 | 若升 v3，显式保留各版本解析与迁移链 |

只删除 23:59 钳制会产生可复现的问题：时钟已进入 Day 2，而生产与商店仍标记 Day 1，保存被现有校验拒绝。

旧跨日协调器在末尾提交商店，失败回滚时间/农田/畜牧；它不是任意多次日结的整体事务。若直接循环调用并在后一次失败，前一次商店提交不能靠现有回滚恢复。

## 6. 存档迁移：需要单独确认

建议使用明确的新 schema 记录自然日期与结算进度的不同含义，而不是在 v2 中悄悄改变 `LastProcessedDay` 语义。当前 JSON 文件足够承载这些字段，不需要数据库。

特殊样例：旧 v2 存档为 Day 2 01:00，旧规则要求生产与商店均已结算至 Day 2；新规则若以 05:00 为边界，该时刻通常尚未完成 Day 2 的晨间结算。直接用新公式覆盖旧标记可能重复成长或重新生成库存。

推荐优先保留旧档时刻、全部资产和已完成的结算事实，迁移时明确记录下一次尚未处理的边界；例如旧档已结算 Day 2，则跳过即将到来的 Day 2 05:00，从 Day 3 05:00 恢复常规结算。代价是首个过渡周期与新开档不同，需要说明并覆盖测试。

该宽限只影响已执行过的生产/补给，Day 2 的 NPC 个人日程仍照常推进；新 schema 校验必须表达这个过渡状态，而非只允许一个由当前钟面推算出的结算编号。

较简单的备选是保留时刻和资产，只把旧档凌晨的结算标记由 D 改为 D−1，下一个 05:00 正常结算。这避免迁移宽限状态，但会让旧档 Day 2 04:59 在一分钟后再获得一次日结机会。另一备选是把旧档时间规范化到晨间，会改变玩家保存的时刻和居民日程。三者均不应在未确认时静默实施。

实施前应通过迁移表确定上述行为、Day 1 清晨的合法初始标记、损坏存档的拒绝规则，以及重复迁移结果。不能仅把版本常量由 2 改成 3：当前 v2 解析入口也依赖该常量。原存档需保留可恢复副本。

## 7. 待实施的 TDD 验收矩阵

以下使用 05:00 作为参数化测试示例，不代表该时刻已获批准。

| 用例 | 必须可观察的结果 |
| --- | --- |
| 23:59 → 次日 00:09 | 自然日期递增；生产和库存不因午夜自动更新；状态可保存 |
| 04:59 → 05:09 | 晨间结算恰好一次，不漏边界 |
| 恰好 05:00、重复同一时刻、恢复 05:00 存档 | 不重复补给或成长 |
| 白天睡 2 小时，不跨结算点 | 只推进时间及相关日程，不发放全天产出 |
| 23:00 睡至次日 07:00 | 跨午夜、晨间结算、个人出门时点分别生效 |
| 连续小步与一次快进 | 无中途操作时，领域状态与目标时刻一致 |
| 多周期后某个参与者失败 | 整个请求的时钟、经济、生产、结算标记保持原值 |
| 自动推进、成功/失败睡眠、保存、成功/失败加载 | 余量遵守各自约定；失败不发布新的 NPC 目标或行程状态 |
| 成长但未浇水、动物未喂食、已有待领取产物 | 保持现有生产限制，不因快进绕过条件或丢失产物 |
| 四名 NPC 设不同出门/返家时刻 | 目标独立；实际到达与目标分开；不生成经济产物 |
| NPC 日程跨午夜或快进中受阻 | 不错用日期、不穿墙、不把受阻者报告为到家 |
| 暂停/失焦后恢复 | 不补算暂停的现实时间；睡眠命令能主动推进 |
| v1、v2 凌晨、v2 白天及新 schema 往返 | 时刻/资产按迁移约定保留，无重抽库存、重复结算 |
| 负数、非有限现实时间、日期溢出、过大请求 | 拒绝后不改变任何状态 |

本轮没有增加或运行这些测试，矩阵是后续实施的验收输入。

## 8. 交付顺序与文档关系

1. 确认时间规则和迁移样例；再更新 ADR-0013 的相关条目、ADR-0011/0012 约束、领域词汇和 T1 验收要求。
2. Runtime 先在未接线模块中测试跨午夜与跨结算点，建立唯一推进用例；随后覆盖失败原子性与存档迁移。每个切片先有失败测试，再实现。接入实际走时前必须同时完成新日期关系下的保存、加载与失败处理，不能交付“可走到凌晨但无法保存”的版本。
3. 接入正常走时与睡眠选择；验证暂停、余量、读档和 UI，不在此切片加入体力、昏倒惩罚或出货箱。
4. 在 T1 的居民日程切片中加入个人配置、跨午夜和快进结果；保留路线、实际到达及经济无副作用约束。
5. 自动化通过后进行场景人工验收；真实 AI 接入仍受原人工场景门禁约束。
