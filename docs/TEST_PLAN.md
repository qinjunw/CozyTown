# Cozy Town MVP 测试计划

## 1. 文档状态与范围

- 适用版本：可玩 MVP；M4 已完成；A1 独立美术阶段正在进行。
- Unity 版本：`6000.5.5f1`。
- 测试框架：`manifest.json` 请求 Unity Test Framework `1.4.5`，Unity `6000.5.5f1` 实际解析内置 `1.7.0`。
- 当前状态：两个 EditMode 测试程序集包含 169 个用例，PlayMode 测试程序集包含 27 个用例；2026-08-30 将 Production UI 面板重建为近黑纯底与三层暖棕木框后，全量批处理结果分别为 169 passed 与 27 passed，均为 0 failed、0 skipped。
- 当前边界：M4 已自动化 schema v1 JSON 单槽存档、五模块保存恢复与回滚、AI 代理编解码与故障回退、状态越权隔离和 Presenter 生命周期。A1 已完成 Production 资源门禁、Scene-01a 世界表现、Scene-01b 运行时状态表现和 Scene-01c Production UGUI 接线；自动化已停在人工场景验收前。真实 AI 驱动 NPC、30 条评测、延迟与成本统计、Windows 构建和录屏在 Scene-01 验收后进入 M5。

本计划覆盖时间、背包、经济、商店、种植、畜牧、钓鱼、烹饪、NPC 对话、AI 对话边界和存档系统。框架阶段验证模块职责、公开契约、状态转换与跨模块闭环，不验证美术质量、数值平衡、复杂 NPC 日程、季节、天气、战斗或野外地图。

## 2. 测试目标

1. 每个模块可通过公开接口独立构造和验证，不依赖场景、MonoBehaviour 生命周期或真实网络。
2. 物品、金币、时间和生产状态只有明确的所属模块能够修改。
3. 跨模块操作满足原子性：失败时不扣除金币或材料，也不产生部分结果。
4. AI 仅生成受约束的对话结果，不直接修改背包、金币、农田、动物、任务或存档。
5. 存档往返后恢复可持久化状态；不兼容或损坏数据产生可识别结果，而不是静默生成部分状态。
6. 一条从购买到生产、烹饪、出售、进入下一天并重新读取存档的经济闭环可以复现。

### 3.1 测试夹具

纯逻辑和组件测试使用测试内构造的最小定义，例如：

- 物品：土豆种子、土豆、鱼、鸡蛋、盐、烤土豆。
- 配方：一个有效配方和一个材料不足配方。
- 商店：一个可购买条目和一个可出售条目。
- 农田：一块可种植地块，作物成熟天数固定。
- 动物：一只鸡，喂食后次日产生一个鸡蛋。
- NPC：一个固定身份、固定回退文本的测试 NPC。

正式场景另保留 EditMode 资产测试和 PlayMode 闭环测试，显式读取 `CozyTown_Dev.unity`。资产测试验证七个交互点、Visual 层级、组件引用和窄接口装配；PlayMode 测试使用默认内容对象图，验证移动、输入恢复、4 名 NPC、存档入口，以及购买、种植、畜牧、钓鱼、跨日、烹饪、出售和再次投入。

### 3.2 测试替身

当前测试按端口提供最小替身：

- AI 客户端替身：返回成功、超时、空结果、非法标签或异常。
- 存档与模块替身：模拟空槽、保存失败和恢复失败，并验证成功回滚到调用前状态。
- 文件测试在测试独占的临时目录中运行，结束时清理，不访问应用持久化目录。

测试替身不得复制业务规则；业务判断仍由被测模块完成。

## 5. 系统契约

以下条目描述测试可观察的行为，不规定类名或内部实现。Runtime API 稳定后，测试名称应映射到这些契约。

### 5.1 时间系统

- 日期只能通过明确的“进入下一天”操作递增一次。
- 日期推进发布一次可订阅事件或返回一次等价结果；同一模块不得同时依赖两种通知路径重复处理。
- 日期推进触发生产模块结算时，每个订阅模块每一天只结算一次。
- 无效日期或重复载入不得使日期倒退。

### 5.2 背包系统

- 增加正数量物品后，物品数量按输入增加。
- 移除数量不超过库存时成功，并扣除准确数量。
- 移除数量超过库存时失败，库存保持不变。
- 零数或负数输入被拒绝，库存保持不变。
- 未知物品标识不能产生可用库存记录。
- 背包只存数量和物品标识；价格、配方和生产规则由对应定义或模块拥有。

### 5.3 经济与商店系统

- 金币增加和扣除只接受正数量。
- 余额不足时购买失败，金币和背包均保持不变。
- 背包无法接收物品时购买失败，金币保持不变。
- 出售仅使用商店定义的售价；出售成功后同时扣除物品并增加金币。
- 未知商品、不可购买商品或不可出售物品返回明确失败结果。
- 同一次购买或出售只产生一次资产变更。

### 5.4 种植系统

- 空地可种植有效种子；非空地或无种子时操作失败且不消耗种子。
- 浇水只改变允许浇水的已种植地块状态。
- 只有满足成长条件的日期推进才增加成长进度。
- 未成熟作物不能收获；成熟作物收获后向背包增加定义产量并重置地块。
- 背包不能接收产物时，地块保持成熟状态，不丢失作物。

### 5.5 畜牧系统

- 饲料存在且动物当天未喂食时，喂食成功并扣除一份饲料。
- 重复喂食或饲料不足时失败，不额外扣除物品。
- 已喂食动物在下一天结算时产生一次产物；未喂食动物不产生。
- 产物未领取或背包无法接收时保留可领取状态。
- 日期推进后重置当日喂食状态，但不重复生成已结算产物。

### 5.6 钓鱼系统

- 有效钓鱼结果只产生定义表中的一种鱼及正数量。
- 失败结果不增加背包物品。
- 背包无法接收时不丢弃奖励，并返回可处理的失败结果。
- EditMode 测试向 `Catch(int roll)` 传入固定值，覆盖成功、失败和物种选择。

### 5.7 烹饪系统

- 已知配方且材料充足时，准确扣除所有材料并增加一份料理。
- 任一材料不足时失败，所有材料数量保持不变。
- 输出无法加入背包时失败，材料保持不变。
- 未知配方或零产量配方被拒绝。
- 配方只引用物品定义；配方服务不负责购买、种植、钓鱼或畜牧结算。

### 5.8 NPC 与对话系统

- NPC 定义包含稳定标识、显示名称、人设信息和固定回退文本。
- 对话上下文只读取允许字段：NPC 身份、当前日期或时段、玩家近期活动、代表性物品、熟悉度和关键记忆。
- 对话结果只包含展示文本及允许的表现标签；未知标签被拒绝或归一为安全默认值。
- 固定对话路径不依赖网络，始终可用。

### 5.9 AI 对话边界

- Unity 客户端通过抽象对话提供者请求结果，不保存服务端密钥。
- AI 成功且结构有效时显示生成文本。
- 超时、网络错误、服务异常、空文本、无效结构或非法表现标签均返回该 NPC 的固定回退文本。
- 回退结果不得修改金币、库存、地块、动物或日期。
- AI 返回的文本即使包含“赠送物品”“扣除金币”等内容，也只作为文本显示。
- 日志可区分成功、超时、结构无效和回退，但不得记录密钥或完整敏感请求头。

### 5.10 存档系统

- 存档包含明确的模式版本号。
- 往返序列化保持日期、金币、背包、农田、动物和必要对话状态等价。
- 运行时缓存、服务实例、事件订阅和密钥不进入存档。
- 缺失存档返回“无存档”结果，不伪装成读取成功。
- 损坏 JSON、未知版本和缺少必需字段返回可识别错误，不覆盖原文件。
- 保存过程先产生完整数据，再替换目标；失败时保留上一份有效存档。
- 同一模式版本内新增可选字段必须具有确定默认值。

## 7. 跨模块经济闭环场景

### LOOP-01：购买、生产、烹饪与出售

前置数据使用测试固定值，价格和产量不依赖正式平衡表。

1. 创建第 1 天、固定初始金币和空背包。
2. 从商店购买一份土豆种子和一份盐。
3. 断言金币减少量等于两项买价之和，背包各增加一份。
4. 在空地播种，断言种子减少一份。
5. 浇水并推进到配方所需作物成熟日；每天只结算一次成长。
6. 收获土豆，断言地块重置且背包获得定义产量。
7. 制作烤土豆，断言土豆和盐按配方扣除，料理增加一份。
8. 向商店出售料理，断言料理减少一份，金币增加定义售价。
9. 使用出售所得再次购买一份生产资料，断言背包取得下一轮投入。
10. 断言最终金币等于“初始金币 - 首轮买入成本 + 出售收入 - 再投入成本”，且任何失败步骤均未留下部分资产变更。

### LOOP-02：日结、畜牧和存档恢复

1. 购买或预置一份鸡饲料，给鸡喂食。
2. 保存第 1 天状态并执行存档往返读取。
3. 从读取结果进入下一天，断言日期只增加一次并生成一个可领取鸡蛋。
4. 领取鸡蛋，再次调用同一天结算入口，断言不产生第二个鸡蛋。
5. 保存并读取，断言日期、金币、背包、喂食状态和产物状态等价。

### LOOP-03：钓鱼食材进入配方

1. 向 `Catch(int roll)` 传入命中一种已知鱼的固定值。
2. 完成一次成功钓鱼，断言背包增加对应鱼。
3. 预置配方所需商店材料，完成烹饪。
4. 断言鱼和商店材料准确扣除，料理增加一份。

## 8. AI 失败与安全场景

每种失败输入必须单独测试，以便定位回退原因：

| 输入 | 预期结果 |
|---|---|
| 请求超时 | 返回当前 NPC 的固定回退文本，原因标记为超时 |
| 网络异常 | 返回固定回退文本，原因标记为传输失败 |
| 提供者抛出异常 | 异常被边界捕获，返回固定回退文本 |
| 空文本 | 判定无效并回退 |
| 缺少必需字段或 JSON 无法解析 | 判定结构无效并回退 |
| 未知表现标签 | 拒绝标签或替换为安全默认值；文本处理遵循已确定契约 |
| 文本声称修改资产 | 只展示文本，所有游戏状态保持不变 |

若实际 Runtime 将解析、校验和回退拆为不同组件，应分别测试各组件，并保留一条从提供者到最终对话结果的集成测试。

## 9. 存档兼容策略测试

MVP 首个模式版本记为 `v1`；实际常量名称以 Runtime API 为准。

- `v1 -> v1`：完整往返，关键字段等价。
- `v1` 缺少可选字段：加载成功并使用文档化默认值。
- `v1` 缺少必需字段：加载失败并返回字段错误。
- `v0` 或未来版本：在没有迁移器时返回不支持版本，不尝试猜测字段。
- 损坏内容：返回解析错误，原始存档保持不变。
- 保存中断：上一份有效存档仍可读取。

引入第二个模式版本时，必须新增版本夹具和迁移测试，再允许修改读取路径。测试夹具不得直接覆盖上一版本样本。

```powershell
  -logFile '<project-root>/Logs/EditModeTests.log'
```

运行 PlayMode 时，将 `-testPlatform` 改为 `PlayMode`，并把结果和日志文件名改为 `PlayModeTests.xml`、`PlayModeTests.log`，避免覆盖 EditMode 证据。

命令不附加 `-quit`，由 Unity Test Framework 在测试结束后关闭批处理进程。附加 `-quit` 可能在测试运行器写出 XML 前结束 Editor。

验证结果必须同时满足：

1. 对应平台的 XML 存在且本次运行时间匹配。
2. XML 中失败数为 `0`。
3. 对应平台的日志不包含编译错误、未激活许可证或测试运行器异常。

Windows 上 Unity 启动器可能先返回退出码 `0`，而编辑器进程随后在日志中报告失败。因此不得只使用 PowerShell 的 `$LASTEXITCODE` 作为通过依据。

## 11. 人工验证步骤
